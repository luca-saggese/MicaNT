# MicaNT — User-Mode Font Engine: TrueType, OpenType and Desktop Typography

**Document:** `docs/USERMODE_FONT_ENGINE_TRUETYPE_OPENTYPE_SPEC.md`  
**Status:** Proposed implementation specification; not evidence of functional bare-metal font rendering  
**Target:** AMD64, C++23, canonical modular NT-compatible kernel, PE64 Ring 3, QEMU/OVMF  
**Owners:** User-mode font engine, GDI32/Win32k client, DirectWrite/text-layout layer, Explorer and compositor. Kernel provides existing Io/FsRtl, Mm, Ob, Ps, Se facilities.

## 1. Purpose and initial success criterion

Implement a real, secure, scalable font-rendering pipeline for user-mode applications. The first observable outcome is an actual `.ttf` file loaded from a mounted volume in QEMU, parsed and rasterized in Ring 3, then used to draw readable, antialiased text in the real Explorer desktop/taskbar and window titles. Do not treat static bitmap text, a hosted renderer, an API declaration, or a screenshot generated by the boot path as acceptance.

The engine must support progressively TrueType outlines in `.ttf`, OpenType fonts including TrueType-flavored `.otf`/`.ttf` and CFF/CFF2 outlines as separately verified, Unicode character mapping, metrics, font selection, caching, layout and fallback. Expose appropriate Windows-compatible GDI and DirectWrite surfaces without making a complete Windows typography stack a prerequisite for the first desktop.

**Non-goals of F0–F2:** building a font parser in Ring 0; importing a separate window manager; shipping proprietary Microsoft fonts; claiming native ClearType parity; requiring a working 3D GPU; interpreting all OpenType tables; full international complex-script layout before baseline text appears.

## 2. Baseline to verify before coding

Repository inspection has identified `include/micant/shared/font8x8.hpp`, `include/micant/um/subsystems/winuser/gdi32.hpp`, `tools/dlls/gdi32.cpp`, `include/micant/um/subsystems/graphics/dwrite.hpp` and the existing Win32k/GDI software presentation path. The presence of GDI/DirectWrite types does **not** prove a functioning freestanding TTF parser, actual glyph rasterization, font enumeration, or Explorer consumption.

At the start of implementation, inspect `AGENTS.md`, `docs/KERNEL_ARCHITECTURE.md`, `docs/KERNEL_INTEGRATION_STATUS.md`, `docs/KERNEL_GPU_DRIVER_IMPLEMENTATION_SPEC.md`, `docs/USERMODE_IMAGE_CODEC_AND_WALLPAPER_SPEC.md`, build targets and real call sites. Classify each capability as declared, hosted-only, compiled, linked, entered in CPL3, verified in QEMU, or tested on physical hardware. Record revision and exact test invocation. The earlier assessment is not a substitute for rechecking current source.

Do not introduce `micant/km/` private includes into Ring 3. Any shared ABI uses fixed-size, versioned and validated contracts in approved shared headers, and rendering follows the canonical compositor/graphics service.

## 3. Architectural ownership

```text
PE64 applications / Explorer / LogonUI                         Ring 3
              |  GDI32 / DirectWrite-compatible APIs
              v
         Font Manager / Cache                                    Ring 3
              |                 |
       Typeface parser      Text shaping/layout                  Ring 3
              |                 |
       Glyph rasterizer ------> BGRA8/alpha glyph atlas          Ring 3
                                      |
                             Window surface/compositor           Ring 3
                                      |
                         Graphics service / VirtIO-GPU          Ring 0

      Io/FsRtl: font file reads; Mm: mappings; Se/Ob: access checks
```

- **Font engine Ring 3:** parses files, loads outlines, calculates metrics, rasterizes and caches glyphs. Parsing untrusted files in kernel mode is prohibited.
- **GDI32/Win32k client:** font objects and API compatibility; resolves logical fonts to physical faces, requests glyph runs and blends text into owned surfaces. Kernel Win32k remains the canonical authority for window and surface access, not font-file decoding.
- **DirectWrite:** compatible factory, font collection, font face and text layout interfaces through a single underlying font engine; no duplicate rasterizer or independent font registry.
- **Explorer / LogonUI:** chooses UI fonts and draws labels using real font API calls. Secure logon text must not depend on a user-modifiable font file or permit untrusted process access to the secure desktop.
- **Compositor:** accepts premultiplied BGRA or alpha surfaces, composites and presents; no font parsing in the compositor or device miniport.
- **Kernel:** mediates I/O and memory, protects security boundaries and does not expose arbitrary file contents to privileged rendering paths.

## 4. File formats and staged compatibility

| Format | Initial scope | Later scope |
|---|---|---|
| TTF / sfnt with `glyf` and `loca` | F0/F1: single-face, essential tables, quadratic outlines, grayscale | Variable axes, advanced hints, embedded bitmaps |
| OTF with TrueType outlines | F3: shared sfnt handling | Full compatibility matrix |
| OTF with CFF/CFF2 | F4: optional explicit backend | Variations and advanced layout |
| TTC / OTC collections | F3/F4: selection and face indexing | Full collections and sharing |
| WOFF / WOFF2 | Not required for native desktop | Browser/web-text integration |
| Bitmap FON and boot 8×8 | Existing fallback kept | Compatibility path as needed |

Do not infer supported encodings, tables or raster formats solely from extensions. Detect signatures, validate table directories and report unsupported variations explicitly. Fonts can use different Unicode mappings and outlines; separate glyph lookup from rendering.

## 5. Third-party engines and licenses

Prefer evaluating mature, actively maintained upstream **FreeType** for font parsing/rasterization and **HarfBuzz** for advanced shaping instead of developing complex parsers from scratch. Confirm precise version, license, redistribution obligations, source provenance, ABI, target cross-compilation and freestanding/CRT dependencies before integrating. Do not import a Linux kernel module or hosted graphics runtime as a bare-metal dependency.

An initial small TTF subset implementation is acceptable only if it is bounded, tested on malformed input, and does not duplicate a more complete engine indefinitely. HarfBuzz is not necessary for a minimal Latin/Western proof, but is required for robust complex-script shaping. Do not use Microsoft proprietary font binaries unless separately licensed; package an openly redistributable TTF fixture and retain its copyright/license notices.

## 6. Font file loading and lifetime

F0 file path example: `C:\Windows\Fonts\DejaVuSans.ttf` (illustrative; use the actual staged fixture path). Load from the mounted volume through canonical user-mode file APIs and Io/FsRtl. Do not embed the expected glyphs as generated bitmaps or use host filesystem access at runtime.

1. Open by handle and apply ordinary Se/Io access checks.
2. Determine true file length; reject zero-length, overlarge and changing/invalid files. Use overflow-safe sizes.
3. Read into an owned buffer or map a verified read-only file section; keep source alive as long as parser-owned tables are referenced.
4. Parse/validate entire sfnt directory and required tables before publishing the face.
5. Apply face-specific resource quotas; release all tables, glyph caches and references on failure, process termination and font removal.
6. Cache shared read-only face data where safe, but never share writable glyph buffers across security contexts without access control.

Handle concurrent font replacement or deletion with a defined snapshot/lifetime policy. Cache keys must contain stable content identity or generation as appropriate, not pathname alone.

## 7. Parser and bounds invariants

For TrueType, validate the sfnt offset table, record count, each table offset/length, non-overlap where required, integer overflow and required fields. The baseline needs: `head`, `maxp`, `cmap`, `hhea`, `hmtx`, `loca`, `glyf`, `name` and optionally `OS/2`, `kern`, `post` according to the supported profile. Enforce valid `indexToLocFormat`, glyph indices, contours, point counts, offsets and transform recursion bounds for composite glyphs.

Explicitly bound:

- Face and file size, table count and table lengths.
- Total glyph count, contours, points, components and composite nesting depth.
- Coordinate multiplication, fixed-point conversions and transformations.
- Allocated pixels and atlas memory; width, height, stride and pitch overflow.
- Instruction/hinting interpreter resources and execution budget if hinting is enabled.
- OpenType shaping recursion, substitutions and expansion if applicable.

Reject malformed fonts deterministically, with no out-of-bounds reads/writes, integer wraparound, unbounded loops, heap corruption or privileged impact. Fuzz parsing and glyph outlines on the host before Ring 3 deployment. Full hinting bytecode is optional initially; disable unsafe/unfinished interpreters rather than attempting partial execution.

## 8. Character mapping and Unicode

Use actual Unicode `cmap` subtables, beginning with validated BMP and supplementary-plane mappings supported by the chosen engine. Distinguish UTF-16 code units from Unicode scalar values; reject malformed surrogate pairs or apply a documented replacement policy. Missing code points must resolve to fallback faces or a replacement glyph, not arbitrary memory.

For F1, support Western Latin text, accented Italian characters, digits and punctuation. Cover `è`, `à`, `ò`, `ù`, `é`, quotation marks and combining sequences with explicit visual tests. F4 adds bidirectional layout and complex-script shaping in the user-mode layout engine, not in GDI kernel code.

## 9. Metrics, rasterization and blending

The engine must provide ascender, descender, line gap, units per em, advances, bearings, glyph bounding boxes, kerning where supported, and a mapping from logical font size/DPI to pixel dimensions. Keep baseline correctness independent of DPI assumptions.

F1 pipeline: selected face + size → glyph outline → grayscale antialiased alpha mask → glyph run → blend into BGRA8 surface. Clip every pixel write to the target rectangle. Respect pitch and alpha convention; avoid straight-versus-premultiplied confusion. Implement stable subpixel positioning policy, optional hinting and optional gamma tuning only after baseline correctness.

Use an 8×8 bitmap fallback for panic/boot diagnostics, not as proof of TTF support. CPU SIMD may accelerate the raster/blending loop later but is not required. GPU acceleration is separate from glyph rasterization and cannot be claimed from VirtIO scanout alone.

## 10. Logical fonts and font manager

Provide a single font collection and resolution service with:

- Family name and optional localized names.
- Style, stretch, weight, size and DPI properties.
- Font registration/removal and enumeration.
- Per-user font installations only after account/profile support is available.
- System font directory and an explicit baseline UI default.
- Resolution rules for missing families and code points.
- Deterministic fallback chains and a non-removable emergency fallback.
- Thread-safe cache and file lifetime management.

Separation is mandatory between installed fonts, loaded font faces, logical font objects (`HFONT`) and cached glyph bitmaps. Refcounts/handles must not silently alias resources owned by another process. Untrusted processes cannot register a font into a privileged global collection without policy validation.

## 11. GDI / Win32 text API integration

Prioritize APIs actually reached by Explorer and LogonUI, especially:

- `CreateFontW` / `CreateFontIndirectW` as required by call sites.
- `SelectObject` font selection and `DeleteObject` resource lifecycle.
- `TextOutW`, `ExtTextOutW` and `DrawTextW` as required by real UI paths.
- `GetTextMetricsW`, `GetTextExtentPoint32W`, `GetGlyphIndicesW` as needed.
- Font enumeration and lookup through the shared manager.

Preserve function signatures and failure semantics, including invalid handles, unsupported flags, clipping, character counts, background modes and text alignment. Do not write successful-looking stub output. The kernel-side Win32k call boundary must stay narrow and user-pointer safe; all actual glyph rasterization belongs in Ring 3.

The initial target is real text in a user-owned window surface. Test in both memory DC/DIB and the compositor's presentation path. Do not conflate passing a hosted GDI test with an actual QEMU frame.

## 12. DirectWrite, text layout and shaping

F3/F4 can surface `dwrite.dll` functionality backed by the same font engine. Introduce interfaces incrementally: factory, system font collection, family, face, glyph metrics, text format and simple text layout. Ensure COM reference/lifetime rules if exposed across standard ABI boundaries.

For advanced typography, integrate HarfBuzz or an equivalent audited shaping engine for OpenType `GSUB`/`GPOS`, ligatures, combining marks and bidirectional scripts. Handle script segmentation and bidi ordering at the layout layer. Unicode normalization is not a substitute for shaping. Do not claim Uniscribe/DirectWrite coverage based on type declarations alone.

## 13. Atlas, cache and concurrency

Cache immutable parsed faces and glyph masks indexed by face identity, size, transform, hint mode and rasterization options. A shared glyph atlas may improve repaint speed. Record memory budget and eviction policy; do not cache unbounded size/transform variants. All cache entries need owners, references and safe eviction while outstanding rendering operations exist.

Include cache invalidation when font files or session settings change. Resolve race conditions among font enumeration, loading, access checks, rendering, logout and process exit. Treat a compositor window and its text surfaces as independent lifetimes.

## 14. Profiles, registration and persistence

Stage a legal open-source baseline font in the boot image and load it through normal file I/O. When Registry/Cm and user profile functionality is ready, implement font registrations and per-user settings persistently; avoid hardcoding admin-specific paths. A missing or corrupt font file must revert to the emergency fallback without blocking login or Explorer.

The font engine must not depend on UnaryFS; it may use the canonical mounted namespace and benefit transparently from UnaryFS layering when available.

## 15. Security and fault isolation

Font files are hostile inputs. Keep the parser in the least-privileged Ring 3 component practical. A malformed font must not crash the kernel, corrupt another process, escape its token or compromise LogonUI. Use strict length checks, per-face quotas, clean resource ownership and bounded allocation.

Security-sensitive UI must use trusted font sources: do not let an unprivileged desktop process replace the font drawn by LogonUI's secure desktop. Validate shared surfaces and font cache handles across processes. Avoid loading third-party plugin codec modules in the privileged login process without an explicit trust model.

Add negative tests for truncated `cmap`, invalid table directory, composite cycles, pathological point counts, extreme DPI, oversized glyph metrics, invalid UTF-16, cache races and font file mutation during use.

## 16. Build and deployment

Create the minimum necessary Ring 3 target(s) and integrate them with the existing PE64 DLL/application startup pipeline. Do not import hosted C++ libraries across kernel/user boundaries or assume Linux userland libraries exist at runtime. Any third-party build must use the approved cross compiler and reproducible pinned sources/patches.

Bundle known-license `.ttf` fixture(s) into the QEMU disk image. Verify the staged bytes from within MicaNT rather than proving only that the host-side file exists. Do not make an unrelated CMake/CRT refactor part of the font milestone.

## 17. Implementation stages and checkpoints

### F0 — Real font file and glyph proof

- Enumerate current font/GDI implementations and establish source-level gap matrix.
- Stage a distributable TTF on the QEMU filesystem with license provenance.
- Open/read/memory-map it via the canonical Ring 3 path.
- Parse required tables and obtain Unicode glyph indices and metrics.
- Render an actual glyph into an owned pixel buffer, verifying its visible shape and bounds.

**Acceptance:** QEMU executes the user-mode font test on the staged TTF and presents or checks real rasterized glyph pixels. A hosted-only or embedded-bitmap result does not pass.

### F1 — Antialiased text and UTF-16

- Implement face sizing, grayscale masks, positioning, clipping, metrics and basic kerning.
- Handle Latin-1/Italian accents and UTF-16 errors.
- Compose short strings on BGRA8/DIB surfaces.
- Verify pixel hashes/regions and glyph metrics against controlled fixtures; tolerance for raster differences must be explicit.

**Acceptance:** Render a visible real TrueType string, e.g. `MicaNT — Città, perché?`, in CPL3 and observe it in QEMU.

### F2 — Explorer/LogonUI and GDI32

- Connect needed font creation, selection and draw APIs to the shared font manager.
- Draw actual taskbar labels and window titles in the canonical Explorer surface.
- Keep boot bitmap font as fallback; error paths must not wedge the compositor.

**Acceptance:** Explorer uses the TTF through real GDI calls; moving/invalidating windows does not redraw stale or corrupt text. LogonUI integration follows secure-desktop isolation prerequisites; no claimed secure login without them.

### F3 — Font manager and OpenType interfaces

- Implement font registration, family enumeration, style resolution, fallback, glyph caches and persistent system settings.
- Provide a bounded initial DirectWrite-compatible face/collection interface.
- Support TrueType-flavored OpenType and collection indexing as separately tested.

**Acceptance:** Switch between two independently installed faces at runtime; fallback and enumeration are observable in user mode and survive restart where persistence is implemented.

### F4 — Complex text and broader font formats

- Integrate shaping engine and bidirectional layout.
- Add support for CFF/CFF2 and TTC/OTC as appropriate to real requirements.
- Test combining marks, Arabic and other complex scripts with validated reference outcomes.

**Acceptance:** Document an explicit format and script matrix; unsupported features fail transparently, not as incorrect glyph substitution presented as success.

### F5 — Quality, performance and acceleration

- Tune glyph atlases, memory budgets, hot-path allocations, subpixel positioning and optional ClearType-like LCD modes.
- Add DPI changes, multi-monitor behavior and font scaling.
- Use CPU SIMD/GPU render paths only after benchmarked parity and verified backend support.

**Acceptance:** No rendering regressions, bounded memory use, robust invalidation under repeated window opens, font changes and logon/logoff; no unsupported GPU-acceleration claims.

## 19. Coordination with adjacent milestones

- **Explorer / compositor:** the font engine consumes stable drawing surfaces and should not be blocked on GPU 3D acceleration. Coordinate GDI API changes and compositor ownership.
- **User logon:** authenticated profiles and secure desktop are prerequisites for claiming user-specific font installation and trusted LogonUI fonts; a bootstrap-only font demo remains valid for F0–F1.
- **Image codecs:** share surface conversion, color conventions and clipping utilities where appropriate, but font parsing and JPEG/PNG decoding remain independent modules.
- **Kernel Mm / Ps:** do not change memory management just to satisfy an oversized glyph; enforce user-mode font resource limits.
- **Legacy monolithic code:** may serve as a documented reference only where `AGENTS.md` permits; no monolithic production linking.

## 20. Implementation rules and definition of done

Maintain one canonical modular kernel and one authoritative user-mode font engine. Preserve changes already in progress, respect Ring 0/Ring 3 separation and do not hide failing tests. Do not declare FreeType, HarfBuzz, DirectWrite, ClearType, OpenType or hardware acceleration operational unless the exact implementation and runtime checks support that claim.

**Minimum desktop outcome (F0–F2):** MicaNT boots in QEMU, a real PE64 user-mode process reads a legal TTF from the mounted image, decodes and rasterizes glyphs, and Explorer paints its text using a real GDI/font path on compositor-owned surfaces. Existing bootstrap, input and graphics tests continue to pass.

**Extended outcome (F3–F5):** installed font enumeration, robust caching, OpenType faces, layout/shaping, quality and optional accelerated rendering each require their own recorded evidence. Never substitute interface completeness or hosted tests for bare-metal verification.
